cam2web · source guide v0.1

三线程，一条链，两级 latest-wins

这个项目干的事很窄：把一块 Linux V4L2 相机的帧，按配置串成一条同步处理链，编成 JPEG， 用 MJPEG 推给浏览器；顺手把相机控件和 ToF 元数据做成 HTTP 接口。 窄带来的好处是边界很清楚——谁拥有 fd、谁跑 CPU、谁面对网络，各归各的线程。

结构拓扑

编译期：谁依赖谁

五个顶层模块是一条单向链：http → runtime → pipeline → v4l → C shim。 看懂回边为零，就知道改动会波及哪里。

线程拓扑

运行期：谁拥有谁

相机 fd 只被采集线程碰；CPU 重的像素活只在处理线程； 网络线程只做转发。三者之间只有队列和 watch。

帧流水线拓扑

一帧怎么变形

从 TOML 声明的 stage 链，到 Layout 逐级协商， 最后一站固定是 JPEG 编码器。中间任何一环返回 None，这帧就消失。

生命周期拓扑

三个 id 把请求绑到资源

node_id / selection_id / session_id： 热插拔、重选、重启预览都会换 id，旧请求自然失效。

一句话 结构就是「没有回边」，线程就是「三个单写者」，流水线就是「配置驱动的纯变换」， 生命周期就是「用 id 做乐观并发控制」，队列就是「永不为了追帧而阻塞」。

这张图在说什么

没有回边

v4l 不知道 pipeline，pipeline 不知道 Session，runtime 不知道 axum。 唯一的小回指是 pipeline 用了 v4l 的两个值类型（CaptureSpec、Captured），这是数据契约，不是控制反转。

状态集中在 L2

除了 Camera 里那几个字段，全项目没有别的地方记录「当前选了谁、预览有没有开」。 HTTP 层是投影：把 Command 发给 L2，把 watch 读出来；它自己不缓存状态。

L3 可单测

pipeline/tests.rs 构造假的 CaptureSpec + Captured 就能跑完整条链，不需要真相机。 这正是把 I/O 全部挤到 L2/L4 换来的。

C 只做 ABI 隔板

shim.c 把 UAPI 的 packed/union 结构和 ioctl 留在 C 里， Rust 侧只处理 repr(C) 的扁平结构。改内核头文件不会把 UB 带进 safe Rust。

配置文件的位置 config.rs 不在这条链上：它是「装配数据」的入口，把 TOML 变成 Vec<DeviceProfile> 交给 L2， 并顺手调用 Pipeline::validate 做一次静态检查。运行期 L4 完全不知道配置的存在。

为什么是这三个线程

T1 为什么不是 async

V4L2 的 poll/ioctl 是阻塞语义，而且 fd 必须单写者。Camera 是一个状态机， 把它钉在一个 OS 线程上，就不需要任何锁来保护 fd、Selection、Device。

T2 为什么要独立

YUV→RGB、最近邻缩放、JPEG 编码全是同步 CPU 活，单帧可能几毫秒到几十毫秒。 放在 tokio worker 上会卡住别的连接；放在 T1 上会拖慢采集。所以单独一条线程，只认队列。

为什么不接着加线程

像素链天生串行（下一级的输入是上一级的输出）。再并行只能按帧并行，而实时预览里 并行只会增加延迟和内存占用，不会提高有效帧率。

关闭顺序是设计的一部分 http::serve 结束后 Service 被 drop → mpsc 发送端归零 → T1 的 blocking_recv 返回 None → 退出循环、stop_preview()、work.close() → T2 的 take() 醒来返回 None。 close() 存在的唯一理由，就是别让 T2 永远睡在 Condvar 上。

两级丢帧，延迟有上界

第一级：T1 → T2

处理不过来时，WorkSlot 只保留最新一帧，旧的直接覆盖并记 dropped_count。 采集线程永远不会因为处理慢而阻塞。

第二级：T2 → 浏览器

watch 只有「当前值」。浏览器解码不及时，中间帧自然被跳过，不会在服务端堆积。 两级都选「丢旧的」，端到端延迟 ≈ 一帧处理时间。

生命周期与装配

三个 id、三次校验、一条启动时序
id生成时机作用域失效后
node_id扫描 /dev/video* 得到路径字符串一台设备节点直接 409：节点不在列表里了
selection_idSelect 成功后 next_id()一次「选中」重选、热插拔、设备错误都会换 → 旧命令 409
session_idstart_preview 成功后 next_id()一次预览停流、重开、设备错误 → MJPEG 连接结束（410/自然结束）
身份不是设备号 DeviceIdentity = (dev, ino, rdev)。/dev/videoN 会被 udev 复用， 所以匹配配置靠 card 名字（去掉 vi-output, 前缀，把 - 换成 _）， 校验仍是 stat 的三个字段。重名直接报「ambiguous」，不做猜测。

校验发生三次，越往后越接近真相

① 加载配置

Config::parse → Pipeline::validate：只按 请求的 FourCC 检查 kind 是否合法、链尾是否为 JPEG。 不碰设备。

② 启动前

start_preview 再 validate 一次：防止配置热更新/请求格式与选中 profile 不一致。

③ 协商后

Pipeline::build(created spec)：用驱动真正返回的 stride_bytes / sizeimage 重算每一级 Layout， 这才是每帧校验的基准。

启动预览的完整时序

  1. T0POST /api/start {node_id, selection_id, format?} → Command::Startformat 省略就用 profile 里的默认值。
  2. T0try_send 后 await oneshot队列满就直接 503，不等。
  3. T1require_target：node_id + selection_id 必须仍然匹配不匹配 = 你手上的状态过期了 = 409。
  4. T1检查 can_stream，按 identity 取 profile没有配置就拒绝（该相机无已知 pipeline）。
  5. T1validate_format + Pipeline::validate在动设备之前把明显错的格式挡掉。
  6. T1stop_preview()：取消扫描、watch 复位、work.clear()、旧 session 快照旧会话先干净地死掉，再谈新会话。
  7. T1device.start：S_FMT → G/S_PARM → REQBUFS(4) → mmap → QBUF×4 → STREAMON失败会回滚（STREAMOFF + 释放 buffer），并把错误串起来。
  8. T1Pipeline::build(协商后的 spec)真实 stride 决定输入 Layout；每一级 output_layout 再验证一次几何。
  9. T1恢复按 profile 名记忆的在线参数设置失败的参数会回退到实际值，并写进 last_error，不影响开流。
  10. T1session_id = next_id()；watch 先发布 {session_id, jpeg: None}，再建 Arc<Session>浏览器可以在这之后立刻订阅 /stream/{id}，等第一帧。
  11. T0返回 status JSON（selection / preview / diagnostics / last_error）前端据此切到 MJPEG 地址，并继续轮询 status 看指标。
失败也想让你看到原因 只有 Invalid 错误会写进 last_error（且只限 Select/Start/Stop/Control/Parameter 这类变更命令）。 Stale 和 Unavailable 是并发/拥塞信号，不污染错误面板。

控件扫描与设备巡检

两条不能阻塞采集的慢路径

控件扫描：把一次大 ioctl 拆成很多小步

读控件可能涉及枚举 + 逐个读值 + 展开菜单，全部做完可能要十几毫秒。做法是只枚举描述符，然后每个事件循环轮次只读一个：

  1. T0GET /api/controls → Request::Controls
  2. T1enumerate_controls 拿到描述符队列，构造 ControlScan
  3. T1每轮 step() 读一个控件（含菜单子项）
  4. T1单步 ≥ 10ms 且正在预览 → 推迟 50ms 再继续
  5. T1扫完一次性回 JSON 数组

扫描期间 Select / Stop / Control 会取消它，responder 收到 Stale → 409。

为什么让 50ms

ToF 的成像依赖 相邻两帧：一半 Depth、一半 NIR，且 sequence 与传感器帧计数都要差 1。 控件读取拖慢采集，就会丢中间帧，配对失败 → 预览一阵一阵地黑。

所以常量是成对出现的：

  • SLOW_CONTROL = 10ms：判定「这一步拖慢了采集」
  • CAPTURE_RECOVERY = 50ms：让采集线程安静地跑几帧

这也解释了 himax_tof_pair 为什么允许 None：丢掉不配对的帧，比合成一张错位的图更好。

身份巡检与设备掉线

周期巡检

每 ≥250ms 对当前路径做一次 stat，比较 (dev, ino, rdev)。 不一致说明节点被拔掉或复用，立刻 invalidate：停预览、清 selection、写 last_error。

被动发现

任何 ioctl 返回 ENODEV / ENXIO / EBADF，track_device_error 会走同一条 invalidate。 poll 的 POLLHUP 映射成 ENODEV、POLLNVAL 映射成 EBADF，殊途同归。

前端看到的是什么 status 里 preview 变回 null，last_error 给出原因；MJPEG 连接因为 session 不匹配自然结束。 用户需要重新「选设备 → 启动预览」，没有自动重连——这是刻意的，热插拔后的节点可能已经不是同一块相机。

失败语义

三条失败路径，三种 HTTP 状态
Failure含义HTTP典型来源
Invalid参数/格式/设备协商失败，重试同样的请求也没用422S_FMT 不支持、FourCC 非法、JPEG quality 越界、没有匹配 profile
Stale你手上的 selection/session 已经过期409重选设备、预览已停、扫描被取消、节点被替换
Unavailable此刻系统忙或不在线503命令队列满（16）、采集线程已退出、已有扫描在跑
410这个 session 已经结束410请求 /stream/{旧id}

每一帧的自检

bytesused 必须落在 min_capture_bytes..=max_capture_bytes： 下界由 Layout 算（含 stride），上界是驱动报的 sizeimage。 驱动标记 V4L2_BUF_FLAG_ERROR 或 bytesused == 0 的帧不进入流水线，只增加 invalid_capture_count。

超时与 EINTR

wait_readable 用绝对 deadline 循环：EINTR 不算失败，重算剩余时间接着等； DQBUF 的 EAGAIN 也回到 poll。20ms 到点就返回 Timeout，主循环继续转，不视为错误。

诊断字段怎么读

字段含义什么时候值得注意
captured_count成功出队的帧数对比相机标称帧率判断带宽/曝光
dropped_countWorkSlot 覆盖旧帧的次数持续增长 = 处理链比采集慢，瓶颈在 T2
invalid_capture_count驱动报错或零字节的帧增长 = 驱动/带宽/格式协商问题，不是 CPU
processing_error_count链上返回 Err 的次数看 last_processing_error 定位到具体 module
capture_fps / output_fps会话开始至今的平均值不是瞬时值；短时间抖动看不出来
last_processing_ms / last_encode_ms最近一帧总耗时 / 其中编码耗时两者接近说明瓶颈就在 JPEG

09

设计不变量

改代码之前先确认它有没有被破坏
fd 只有一个所有者

Device 只在 T1 上被可变借用；T2 拿到的是 Arc<Session>，里面没有 fd。任何跨线程持有 fd 的新设计都要先推翻这条。

DQBUF 之后立刻 QBUF

4 个 buffer 是驱动流水线的全部产能。拷贝是刻意付出的代价，换的是「用户态处理慢也不会饿死驱动」。

队列永远不为了追帧而阻塞

命令用 try_send，帧槽覆盖旧值，watch 只留最新。三处都选择「快速失败或丢弃」，没有一处会反压到相机。

session_id 是发布闸门

T2 发布前比对 output.session_id，MJPEG 读取时再比对一次。这样「旧处理结果」既不会污染新会话，也不会串到别人的连接里。

锁不跨阻塞点

poll_frame 里先 drop(diagnostics) 再 work.push；处理线程先放掉 pipeline 锁再取 diagnostics 锁。没有任何地方持锁做 ioctl、等待或 send。

失败必须清场

开流失败回滚 buffer，编码链构建失败回滚 V4L2，停流失败撤销 selection。没有「半开」状态：session 要么完整，要么不存在。

结构不可变，参数可变

stage 链在 build 时定型；运行期只能通过 set_parameter 改 quality 这类白名单参数。想换链就重开会话。

采集优先于控件与管理

每轮循环只推进一个控件；慢操作之后主动让 50ms。所有「顺手做点别的事」的设计都必须服从这个优先级。

驱动错误统一入口

识别设备丢失的 errno 只出现在 track_device_error 一处；不要在各调用点复制这套判断。

C 侧只暴露 POD

ffi.rs 里的结构必须和 shim.c 的 struct cam_* 一一对应。新增 ioctl 时两边同步改，Rust 侧不要直接声明 UAPI 结构。

10

术语

在这份代码里的具体含义
FourCC

四字节像素格式标识，如 YUYV、RGGB。PixelFormat 是它的内部类型。

Layout

一帧的内存几何：格式 + 宽高 + 每行字节数。所有 stage 的输入输出都用它描述，不靠隐式约定。

stride_bytes

驱动给的行跨度，可能大于有效行宽（有 padding）。required_bytes 只算到最后一行的有效字节。

sizeimage

驱动为整帧分配的最大字节数，是每帧校验的上界；下界由 Layout 算出来。

DQBUF / QBUF

出队 / 入队。出队后 buffer 归用户态，必须尽快入队，驱动才能继续采。

selection

一次「选中某设备」的上下文：fd、能力、匹配到的 profile、selection_id。

session

一次预览：协商后的 CaptureSpec、Pipeline、诊断计数、session_id。

stage

链上的一级，绑定一个模块实例和它声明的输出 Layout。

latest-wins

只保留最新值：帧槽覆盖旧帧，watch 只暴露当前值。用来把延迟钉死在一个常量上。

invalidate

发现设备消失/被替换后的一步到位清理：停预览、清 selection、记录原因。

wrapping_add

ToF 帧计数是 u16/u32 的自然回绕，配对判断用它避免「刚好跨过最大值」时误判。

V4L2_BUF_FLAG_ERROR

驱动标记「这帧数据不可信」。这类帧只计数，不进流水线。
